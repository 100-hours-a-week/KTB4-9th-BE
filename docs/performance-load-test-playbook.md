# COSMOS 성능 최적화·부하 테스트 플레이북

이 문서는 부하 테스트 특강의 핵심 내용과 COSMOS 백엔드에서 성능 실험을 진행할 때 지킬 기준을 기록한다.

## 핵심 원칙

- 코드를 보고 병목을 추측하지 말고 APM과 부하 테스트 결과로 확인한다.
- 목표 TPS와 응답 시간 기준을 먼저 정한다.
- 한 실험에서는 한 가지 요소만 변경하고 동일한 조건으로 다시 측정한다.
- 평균값만 보지 말고 시간대별 TPS, P95/P99, 실패율과 긴 꼬리 지연을 확인한다.
- 로컬 결과만으로 결론 내리지 않고 실제 배포 환경과 유사한 환경에서 검증한다.
- Java 애플리케이션은 충분히 워밍업한 뒤 측정한다.
- 성능뿐 아니라 장애 상황의 안정성과 데이터 정확성도 함께 검증한다.
- 로그처럼 운영과 장애 분석에 필요한 기능을 성능 수치만을 위해 제거하지 않는다.

## 특강의 최적화 사례

| 단계 | 변경 사항 | 평균 TPS |
| --- | --- | ---: |
| 최초 | 기존 서버 | 833 |
| 1 | 불필요한 DB 조회 1회 제거 | 1,589 |
| 2 | 불필요한 트랜잭션 범위 축소 | 3,677 |
| 3 | 반복 DB 조회를 캐시 데이터로 대체 | 7,293 |
| 4 | 로그 파일 I/O 제거 실험 | 약 9,000 |
| 5 | 추가 최적화 후 운영 환경 배포 | 19,578 |

운영 환경에서는 평균 19,578 TPS, 최대 약 25,000 TPS, 평균 응답 시간 약 5ms를 기록했다. 로그 파일 I/O 제거는 성능이 개선됐지만 운영 안정성을 위해 롤백했다.

## 병목 분석 순서

1. APM으로 요청 처리 흐름을 수집한다.
2. k6로 현실적인 트래픽과 사용자 시나리오를 재현한다.
3. k6의 TPS·P95·P99·실패율과 서버의 CPU·메모리·GC·스레드·DB 연결 풀·네트워크를 같은 시간축으로 본다.
4. 느린 요청의 트레이스에서 DB, 트랜잭션, 외부 API, 락, 로그 I/O 가운데 가장 큰 병목을 찾는다.
5. 한 가지 가설만 수정한다.
6. 같은 워밍업, 부하 단계, 데이터, 자원 제한으로 다시 측정한다.
7. 개선 수치와 부작용을 기록한 뒤 다음 병목으로 이동한다.

## 그래프 패턴 해석

- TPS가 더 오르지 않는데 CPU가 낮다: DB 연결 풀 대기, 외부 API, 락, 파일 I/O 등 대기 병목을 의심한다.
- 초반 TPS가 낮다가 오른다: JIT 컴파일, 연결 풀, 캐시 워밍업 부족을 확인한다.
- 평균은 빠르지만 P99만 튄다: GC, 간헐적 파일 I/O, 락과 같은 간헐 이벤트를 확인한다.
- 시간이 갈수록 TPS가 하락하고 메모리가 증가한다: 메모리 누수 또는 GC 압박을 의심한다.
- 애플리케이션과 DB가 여유로운데 처리량이 제한된다: 네트워크 대역폭과 부하 발생기 한계를 확인한다.

## 자주 확인할 병목

- 느린 쿼리와 누락된 인덱스
- N+1 등 반복 DB 호출
- 필요 이상으로 넓은 트랜잭션
- DB 연결 풀 부족 또는 긴 점유 시간
- 순차 외부 API 호출
- 여러 번 나눈 작업 중 일괄 처리가 가능한 부분
- 동기 로그 파일 I/O
- 캐시로 대체할 수 있는 반복 조회

## COSMOS 관측 스택 방향

- 부하 생성: k6
- 메트릭과 k6 결과: Prometheus
- 대시보드와 신호 연결: Grafana
- 로그: Loki + Alloy
- 지속 프로파일링: Pyroscope
- 에러 추적: Sentry
- 요청 단위 분산 트레이싱: OpenTelemetry Java Agent + Tempo 추가 권장

부하 테스트의 `testid`를 실행마다 다르게 부여하고, 실험 조건과 Git 커밋을 함께 기록한다. 최적화 전후 비교에서는 동일한 대시보드 시간 범위와 동일한 테스트 시나리오를 사용한다.

## B0 데일리 배틀 정상 부하 기준선

B0는 이후 복구 로직과 성능 변경 전후에 항상 다시 실행하는 공통 대조군이다.

- 개발 서버에서 서로 다른 사용자 100명이 각각 한 번 참여하고 제출한다.
- 제출 시각은 12:50:00부터 12:59:50까지 균등하게 분포시킨다.
- 워커 2개와 100ms fixed delay 등 서버 설정은 비교 실험 사이에 유지한다.
- 13:00 최초 결과 조회가 모든 사용자에게 `200 OK`를 반환해야 한다.
- 모든 사용자의 상태는 최초 결과 조회 시 `GRADING_COMPLETED`여야 한다.
- 제출 누락·중복, `SUBMITTED`·`GRADING` 잔존, `GRADING_FAILED`는 없어야 한다.
- 최초 측정과 주요 변경 후 측정은 가능한 한 같은 인프라·데이터 조건에서 반복한다.

테스트를 당일 다른 시각에 실행해야 한다면 배틀 구간 전체의 시계 시각만 옮길 수 있다. 예를 들어 20:00~20:10으로 옮길 때도 마지막 제출은 20:09:50, 제출 마감은 20:09:59, 최초 결과 조회는 20:10:00으로 맞춘다. 10분 길이와 제출 분포를 바꾸면 B0가 아니라 별도 시나리오가 된다.

고장 복구는 B0 자체에 섞지 않는다. 복구 로직은 B0의 성능 퇴행이 없는지 먼저 확인한 뒤, B0에 워커 또는 서버 종료 조건만 추가한 별도 장애 시나리오로 검증한다.
